# Automation Runtime UI Contract

Desktop workflow and Automation daemon RPCs use a 120 second timeout. Local
Automation operations can start or recreate the Puffer-managed AgentEnv Docker
Compose runtime, run migrations, seed local credentials, and wait for runtime
health checks before the daemon returns.

Automation Runtime settings display connection test results as three
user-facing steps: API readiness, runtime schema/token validation, and
workspace access. The UI does not show a separate Auth row; token acceptance is
validated by the runtime node-definition step. Daemon responses include the
`ready` check returned by `workflow_backend_test_connection`, and Desktop
renders optional fields only when they are present.

Automation Runtime settings expose local runtime repair only when the backend
mode is `local`. The repair action is disabled while saving, testing, or
another repair is running. Repair uses a browser confirmation dialog before
calling `workflow_backend_repair_local_runtime` with `confirm: true`.

Repair is separate from Test Connection. A failed connection test may report
that Puffer needs to rebuild local runtime data, but the UI does not trigger
that rebuild implicitly because the local runtime database can contain runtime
history and deployed runtime state.

The UI describes repair as Puffer-managed runtime repair and reports success
without showing Docker, Postgres, local URLs, or stack trace details.
