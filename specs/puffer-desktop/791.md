# Automation Builder Activation And Nodes

The desktop Automation screen uses Active and Paused as the long-lived
user-facing lifecycle labels. A saved Automation is Paused until the user turns
on the Active toggle.

Saving an Automation sends a paused record to `automation_save`; it does not
request `status: "enabled"`. The Active toggle first saves the current detail
form as Paused, then calls `automation_compile_deploy`. Only a successful
deploy response with `status: "enabled"` and `runtime.status: "deployed"` makes
the card and detail header show Active. Test runs use `automation_sync_preview`
and `automation_run_preview`; they do not publish live runtime bindings.

Automation detail run history includes a dry-run input editor and latest result
preview. `Test Run` sends the editor contents as `automation_run_preview`
input. JSON objects are sent as the preview trigger payload. Other values are
wrapped as simple `text` input so users can paste a message or event body
without formatting it. The result preview shows latest test run status,
summary, structured result JSON, or error, and run history refreshes after the
preview request completes.

New Desktop Automations serialize the primary hidden instruction step as a
Puffer product agent node:

- `node_type: "puffer_agent"`
- `config.instructions`
- `config.tools`
- `config.permissions`

The Automation compiler treats this product node as a Puffer-owned runtime
boundary. It is omitted from AgentEnv workflow definitions, and downstream
AgentEnv work is compiled into a continuation segment keyed by the
`puffer_agent` step id. Desktop does not emit a default `transform_js`
instruction placeholder for new specs and does not expose `puffer_agent` as a
selectable tool. Provider-specific LLM nodes continue to use their own AgentEnv
node contracts.

The Desktop Automation UI requires a real trigger source before saving.
Connector event catalog entries remain selectable in the Trigger picker and
serialize to `puffer_connection` trigger specs. The Webhook option stores an
AgentEnv `webhook` trigger node. Prompt prefill can infer connector triggers
from GitHub, Gmail, Slack, or similar wording, but it does not create a local
draft/manual trigger branch.

Catalog action DTOs include optional `runtime_owner` metadata. Desktop can keep
user-facing "tool" language while distinguishing backing execution:

- `agentenv` tools compile into AgentEnv workflow nodes.
- `puffer` tools are connector-backed daemon actions.

`SelectedAutomationTool` remains the user-facing umbrella type. The Tool picker
filters out `tool_capability` entries, keeps daemon catalog actions whose node
ref is `puffer_connector_action`, and saves selected connector actions as
`agent_env_node` flow steps with catalog-provided connector, connection, and
action config. Connector actions save as flow steps only when they come from
catalog action definitions; execution is owned by the daemon-side Puffer action
bridge, not AgentEnv.

The built-in Local JavaScript Transform appears under `Local Runtime` and saves
the catalog-provided `transform_js` node ref plus UI metadata used for
round-trip editing. The UI does not infer that every connector skill command is
a selectable Automation tool. Fake catalogs use real built-in action slugs when
they model connector-backed tools; Telegram read-message commands remain
internal Telegram tool/subscriber operations until the daemon exposes them in
`automation_catalog.actions`.
