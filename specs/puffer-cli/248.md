# Local Runtime Diagnostics And Repair

Local workflow runtime startup owns the Puffer-managed AgentEnv Docker Compose
stack under `~/.puffer/workflow-runtime`. Before starting the stack, the daemon
detects stale Compose `api` containers from the fixed project when their
config-file label does not point at Puffer's generated compose file, or when
their published API host port does not match the saved local `api_base_url`.

Detected stale projects are removed before the normal start, migrate, seed,
readiness, node-definition, and workspace validation sequence. Puffer preserves
the current local runtime data directory when containers already belong to the
current compose file. The Compose project name is `puffer-workflow-runtime`
unless `PUFFER_WORKFLOW_RUNTIME_PROJECT` overrides it.

The workflow runtime connection test validates `/v1/health/ready` before
checking node definitions and workspace access. Node-definition failures,
including invalid runtime tokens, remain runtime validation failures. AgentEnv
workflow validation errors for missing required configuration surface as
Automation configuration errors.

Automation runtime HTTP calls use the same 120 second timeout as desktop daemon
RPCs so slow local create/deploy requests can finish after runtime startup.

Public error mapping is shared by backend workflow-runtime and local runtime
paths through `automation_runtime_errors`. The mapper covers Docker
availability, stale ports or containers, image pulls, database preparation,
token and workspace access, incompatible runtime responses, unreachable runtime
requests, and AgentEnv workflow validation failures. Daemon logs keep raw
runtime diagnostics; Desktop receives product-facing Automation Runtime error
text without raw local URLs, `/v1/...` paths, Docker Compose output, Postgres
stack traces, or node module paths.

The local runtime repair RPC is explicit and confirmation-gated. It stops the
Puffer-managed Compose project, archives existing non-empty Postgres and Redis
data directories under the local runtime data directory, recreates fresh data
directories, and reruns the normal start, migrate, seed, and validation
sequence. Test Connection never triggers this rebuild implicitly because local
runtime data can contain runtime history and deployed runtime state.
