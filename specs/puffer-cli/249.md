# Automation Daemon Runtime Boundaries

`automation_save` is a save/pause API. It rejects `status: "enabled"` so a
client cannot create an active Automation without live runtime deployment. When
an enabled Automation saves a changed spec, the daemon pauses the record and
leaves runtime artifacts stale until activation runs again.

`automation_compile_deploy` is the activation path. After compile and live
deploy succeed, the daemon enables generated Puffer bindings and then marks the
Automation enabled. The RPC response includes record status and runtime summary
so clients display Active only for `enabled` plus deployed runtime state.

`automation_catalog` exposes connector-backed inputs as `connector_event`
triggers with `puffer_connection` templates. Those triggers compile to
Puffer-owned workflow bindings that run Automations from connector subscriber
events. The catalog exposes `Webhook` as an AgentEnv `webhook` trigger node with
POST support and no authentication.

Catalog actions expose their runtime owner:

- `runtime_owner: "agentenv"` for actions that compile into AgentEnv workflow
  nodes.
- `runtime_owner: "puffer"` for connector-backed actions that persist as
  `puffer_connector_action` flow steps.

The built-in Local JavaScript Transform is an AgentEnv action published as
`transform_js`. Connector action definitions are published as
`puffer_connector_action` node refs with connector, connection, action, schema,
and side-effect gating metadata copied from the connector action definition.
AgentEnv receives only AgentEnv workflow nodes; Puffer owns connector event
triggers, connector action execution, and graph segmentation between AgentEnv
root and continuation workflows.

Connector actions execute through the installed connector action executor in
original flow order. Each connector result becomes `previous_output` for the
next continuation, loop, or connector action. Ungated connector actions run
synchronously.

Top-level connector actions marked `external_side_effect`, `draft_only`, or
`human_approval_required` are approval-gated. Preview and live
connector-triggered runs create an outbound action draft, return
`awaiting_approval`, and persist a continuation suspension when steps remain
after the gated action. Approval uses `connector_action_execute`; after the
real connector action succeeds, the daemon resumes the suspended continuation
or marks a terminal-position run completed. Rejection marks the run
`rejected` and removes its suspension.

The daemon exposes the Automation review queue through
`automation_pending_action_list`, `automation_pending_action_get`, and
`automation_pending_action_reject`. The queue reuses
`outbound_action_drafts.json` with Automation join fields
`automation_id`, `automation_run_id`, and `step_id`; execute-on-approve keeps
the existing draft identity, version, provenance, content-hash, and
idempotency checks.

Inside loop bodies, connector actions are the terminal action suffix. The
daemon runs the compiled loop body workflow, then executes one or more
loop-body connector actions in order for that iteration. No same-body AgentEnv
step runs after that suffix. Human-gated loop-body connector actions and gated
first-class `Agent` step tools are rejected before run time because the daemon
does not yet have a mid-loop or mid-agent review resume point. Top-level
templates such as email reply drafts and PR review comments still use the
normal `puffer_agent -> puffer_connector_action` shape; the suffix rule only
governs connector actions authored inside loop bodies.

Daemon Automation compile and preview sync paths call the shared compiler
without resolving provider/model state. The compiler emits only AgentEnv-owned
workflow segments and Puffer binding plans. It never clones or mutates the
persisted Automation spec with `upstreamId`, `model`, `agentId`, or other
AgentEnv implementation details.

Test preview and connector-triggered live rerun paths execute `puffer_agent` as
a Puffer-owned runtime boundary. The daemon builds a background Puffer session,
loads the selected provider/model and resources from daemon runtime inputs, and
calls the normal Puffer provider loop directly. AgentEnv never sees
`managed_agent_create`, `managed_agent_call`, or dangling templates that depend
on Puffer runner state.

Each `puffer_agent` call receives the current orchestration context:
`trigger`, `root_output`, `previous_output`, `loop_input`, `iteration`, and the
Automation instructions. It returns a structured `puffer_agent_result` with
`done`, `reason`, `next_input`, and `output`.

Open-ended "repeat until done" behavior is owned by the first-class iterative
agent step, not by loop syntax. An `agent` step with `mode: until_done` runs the
Puffer agent each turn, dispatches any `tool_calls` it requests (Puffer-owned
connector actions) and feeds ungated results back, and stops when the agent
reports `done: true` or the `max_iterations` hard cap is reached. `once` mode
runs a single turn. Loop syntax now only supports deterministic `for_each`:
foreach loops pass each item as both `loop_input` and the configured item alias
while preserving `previous_output` from the prior iteration. Preview run
history labels the source event as `preview_run`.

`puffer_agent` boundary failures are mapped to product-facing messages. Missing
provider/model context asks the user to reload daemon runtime inputs; missing
loaded resources does the same for Puffer resources; missing selected provider
credentials asks the user to connect credentials before activating. Raw details
stay in daemon logs. AgentEnv `managed_agent_create` sandbox failures are not a
supported Automation failure mode because compile/deploy no longer emits
managed-agent nodes.
