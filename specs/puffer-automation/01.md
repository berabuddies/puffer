# Automation Product Runtime Boundaries

Persisted Automation specs store product semantics only. Triggers are either
AgentEnv runtime triggers (`agent_env_node`) or Puffer connector event triggers
(`puffer_connection`). Puffer connector triggers compile to Puffer binding
plans and do not create webhook or synthetic ingress nodes in AgentEnv. Root
AgentEnv workflows start at the first flow step unless an AgentEnv trigger is
present.

`puffer_agent` is valid only as an execution step. A trigger whose node type is
`puffer_agent` is invalid. A persisted `puffer_agent` config may contain only
product fields:

- `instructions`
- `tools`
- `permissions`

Runtime fields such as `agentId`, `backend`, `upstreamId`, `workspaceId`,
`content`, `prompt`, and `timeoutSeconds` are invalid at the Automation store
and validation boundary.

The compiler does not resolve agent runtime state and does not emit AgentEnv
managed-agent nodes. The legacy/product `puffer_agent` node ref is a
Puffer-owned runtime boundary:

- AgentEnv nodes before the boundary compile into the current AgentEnv segment.
- AgentEnv nodes after the boundary compile into a continuation workflow keyed
  by the `puffer_agent` step id.
- Loop bodies compile only the AgentEnv segment that Puffer runs for each
  iteration; the daemon executes any loop-body `puffer_agent` node boundary
  after that segment and feeds the structured result into the remaining
  loop-body suffix.
- First-class iterative `Agent` steps are not valid inside loop bodies. The
  `Agent` step owns its own iteration strategy and may expose Puffer connector
  action tools only at top level.

The daemon runner calls the Puffer provider/agent loop directly at each
`puffer_agent` boundary. Its prompt input includes `trigger`, `root_output`,
`previous_output`, `loop_input`, `iteration`, and Automation state. Its
structured output is `{ done, reason, next_input, output }`, wrapped as a
`puffer_agent_result`.

The compiler submits only AgentEnv-supported nodes. `transform_js` and catalog
`webhook` node refs pass through to AgentEnv. `tool_capability` remains
unsupported. `puffer_connector_action` is also a Puffer-owned connector action
boundary: the compiler omits it from AgentEnv and splits surrounding AgentEnv
work into root and continuation workflows. The daemon runner executes connector
actions in original flow order and passes each connector result as
`previous_output` to the following continuation, loop, or connector action.

Inside loop bodies, connector actions are the terminal action suffix. A loop
body may run AgentEnv work, then Puffer-owned `puffer_agent` node boundaries,
then one or more `puffer_connector_action` steps. No non-connector AgentEnv
step and no nested loop may follow the first loop-body connector action,
because Puffer runs the compiled loop body workflow before the connector-action
suffix for that iteration.

Human-gated connector actions are supported only as top-level flow steps in
this pass. Loop-body connector actions and first-class `Agent` step tools are
rejected when they carry `external_side_effect`, `draft_only`, or
`human_approval_required`, because there is not yet a mid-loop or mid-agent
review resume point. Loop Automations are limited to Puffer connector triggers
until AgentEnv trigger ingress is bridged back into the Puffer loop runner.
