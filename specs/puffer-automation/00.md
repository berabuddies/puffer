# puffer-automation 00: Automation storage and compile contract

## Summary

`puffer-automation` owns the user-facing Automation storage contract and the
compile plan that bridges semantic Automations to internal AgentEnv workflow
artifacts and Puffer connector bindings.

The crate exposes Automation specs and records, runtime state, validation,
canonical spec hashing, `AutomationStore`, `compile_automation(record)`, and
`AutomationRunLocation` for daemon/runtime callers that map the stored
execution location to concrete workflow backend modes.

## Semantic Spec

`AutomationSpec` stores `spec_version`, name, optional description, source,
instructions, run location, triggers, linear flow, and review policy.

`run_location` is serialized on the semantic spec, defaults to `local` for
records written before the field existed, and participates in canonical spec
hashing and revisioning. Supported values are:

- `local`: run through the Puffer-managed local AgentEnv runtime.
- `agent_env_cloud`: run through an AgentEnv Cloud runtime.

Triggers are Automation semantics, not persisted binding records:

- `Manual` is for preview/manual runs.
- `AgentEnvNode` is allowed for linear Automations.
- `PufferConnection` reuses connector filter, ignore-filter, and contact-id
  structures until compilation creates generated bindings.

Loops are Puffer-side syntax for deterministic `for_each` iteration only; the
foreach body compiles to a separate AgentEnv workflow artifact invoked per item
by the Puffer runner. Open-ended "repeat until done" behavior is owned by the
first-class `Agent` step (`mode: until_done`, bounded by `max_iterations`), which
is a Puffer-owned runtime boundary and never emitted as an AgentEnv node.
Unsupported loop shapes fail explicitly instead of emitting AgentEnv graphs the
runner cannot schedule.

## Store Contract

`AutomationStore` owns persisted records and initializes metadata on create:
revision 1, `NotCompiled` runtime, timestamps, and empty runtime artifacts.
UI callers cannot write forged runtime state.

User-facing writes include create, save spec, set status, archive, and delete.
Compiler/runner writes include `replace_runtime` for successful compile/deploy
and `replace_runtime_error` for failures.

`save_spec` requires `expected_revision`. Unchanged canonical spec hashes keep
the revision and refresh `updated_at_ms`; changed specs increment the revision,
clear orphanable runtime artifacts, clear old errors, and mark existing
compiled runtime stale.

`replace_runtime` requires runtime `compiled_revision` and `spec_hash` to match
the current record. `replace_runtime_error` writes runtime `Error` with
`last_error` but leaves successful compile metadata empty.

## Runtime Validation

Record validation checks runtime artifacts against the current spec:

- loop-body workflow roles reference loop steps.
- continuation and helper workflow roles reference existing steps.
- generated Puffer bindings reference `PufferConnection` triggers.
- root workflow roles have no source step reference.

This prevents persisted runtime state from carrying orphaned workflows or
bindings after spec edits.

## Compile Plan

`compile_automation(record)` emits an internal `AutomationCompilePlan` keyed by
Automation id, revision, and spec hash. Plans contain typed AgentEnv workflow
definitions and Puffer binding plans, not deployed workflow ids.

Linear AgentEnv steps compile into the root workflow. Puffer connection
triggers produce binding plans with generated slugs of the form
`automation-{automation_id}-{trigger_id}`. Manual triggers do not produce
bindings.

`spec_hash` is the canonical hash of the user-authored `AutomationSpec` only.
It excludes record metadata, runtime state, generated definitions, and deployed
workflow ids. Runtime artifact ids and credentials remain outside the semantic
Automation spec.
