# Monitor Task Text Sanitization

## Summary

Monitor task `subject` and `description` values are sanitized when persisted through `TaskCreate` and `TaskUpdate`, and legacy monitor tasks are sanitized lazily when read by `TaskGet`, `TaskList`, or the daemon workflow snapshot. Runtime persistence now enforces the content-first contract even if a monitor agent writes source-first or judgment-first text.

## Behavior

- Strip source prefixes such as `Telegram message from`, `Incoming Telegram message`, `Telegram user sent`, `In Telegram group`, and `message from chat_id`.
- Remove monitor source terms such as `Telegram` and summary boilerplate such as `message asks`.
- Drop judgment sentences containing terms such as `actionable request`, `actionable task`, `non-actionable`, `likely`, or `triage`.
- Apply the sanitizer case-insensitively for ASCII source and judgment terms.
- Keep source identity in task metadata, not in the user-facing task text.
- Backfill legacy persisted monitor task text on read and save the sanitized value back to the monitor task store.

## Architecture

The sanitizer lives in the workflow task tool runtime next to monitor task metadata validation. Monitor detection uses the target monitor task store, existing monitor metadata, or incoming monitor metadata. Non-monitor task subjects and descriptions are left unchanged.

## Compatibility

Existing persisted monitor tasks are migrated lazily when task list/detail or desktop workflow snapshot reads touch the monitor task store. Session-local non-monitor tasks are not changed.

## Verification

`monitor_task_create_sanitizes_source_and_judgment_language`, `monitor_task_update_sanitizes_source_and_judgment_language`, and `monitor_task_get_backfills_legacy_source_and_judgment_language` assert that monitor task text no longer persists source or judgment boilerplate while preserving the original message content and useful follow-up intent.
